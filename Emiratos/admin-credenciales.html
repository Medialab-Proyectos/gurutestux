Cómo se conecta

OAuth 2.0 · client credentials

Tu sistema no manda el secreto en cada llamada. Lo cambia una vez por un token que caduca, y ese token es el que viaja. Si algún día se filtra, deja de valer solo.

  • 1 · Pide un token
    Con el identificador y el secreto de la aplicación. Te devolvemos un token válido durante una hora.
  • 2 · Llama con el token
    Va en la cabecera Authorization de cada petición, como Bearer.
  • 3 · Pide otro cuando caduque
    Tu sistema lo renueva solo. No hace falta que nadie entre aquí a tocar nada.
Direcciones
Para quéDirección
Pedir el tokenPOST /oauth2/token
Consumir el serviciohttps://api.edoc.ae/v1/
Tipo de concesióngrant_type=client_credentials
Alcancescope=documentos.leer documentos.escribir
Ejemplo, para copiar tal cual
curl -X POST https://api.edoc.ae/oauth2/token \
  -d "grant_type=client_credentials" \
  -d "client_id=alnoor-erp-sap" \
  -d "client_secret=EL_SECRETO_DE_TU_APLICACION"

# Respuesta
{ "access_token": "eyJhbGciOi...", "token_type": "Bearer", "expires_in": 3600 }

# Y a partir de ahí, en cada llamada
curl https://api.edoc.ae/v1/documentos/emitidos \
  -H "Authorization: Bearer eyJhbGciOi..."

Decidido · 2026-09-07 Se toma el modelo de Francia, con OAuth. No una misma credencial para toda la empresa: una por integración, cada una con su ciclo de vida. Lo que hay que trabajar es que configurarlo sea sencillo, sin esconderle lo técnico a quien lo necesita.
Fuera del MVP Certificado o firma digital. La norma de Emiratos no la exige y en Francia las facturas no llegan firmadas. Pedirle al cliente su certificado sin que la ley lo pida sería extralimitarse. Firmar nosotros con el certificado de la casa es otra conversación y sigue abierta.
